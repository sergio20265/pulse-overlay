# ARVEXA Perf — standalone-версия оверлея для не-WordPress сайтов

Дата: 2026-10-15. Статус: дизайн согласован, план реализации — следующий шаг.

## Зачем

Повод — minmagic.ru (Tilda): все страницы тормозили из-за виджета GetReview,
чей сервер `app.getreview.io` перестал отвечать (TLS-рукопожатие висит до
таймаута). PageSpeed этого не показывает, а в HTML сайта ссылки на getreview
нет — скрипт вставляется чем-то другим (вероятно, контейнером
`stat1.clickfraud.ru`). Нашли вручную через curl и разбор HTML.

Цель: клиент сам вставляет код на свой сайт (Tilda, HTML, любой другой),
открывает страницу с `?arvexa=1` и видит, какие сторонние запросы тянут сайт
вниз, кто их подключил, и может отправить отчёт по ссылке подрядчику.

Аудитория первой версии — клиент (сначала главный клиент: minmagic.ru,
wizardia.land). Без регистрации. Интерфейс на русском, с пояснениями
«что это значит и что делать».

## Архитектура

```
сайт клиента                         portal.arvexa.ru (VPS, Next.js 16)
┌───────────────────────────┐        ┌──────────────────────────────────┐
│ <head>                    │        │ nginx → /perf/overlay*.js|css    │
│   инлайн loader (~1.5 КБ) │──?arvexa=1──► (статика, долгий кэш)       │
│   └ перехват вставки тегов│        │                                  │
│ overlay.<hash>.js (async) │──────► │ POST /api/perf/probe             │
│   ядро оверлея + модуль   │        │ POST /api/perf/reports           │
│   «Сторонние скрипты»     │        │ GET  /perf/r/<id>  (отчёт)       │
└───────────────────────────┘        │ GET  /perf  (код вставки, справка)│
                                     └──────────────────────────────────┘
```

Принцип: сайт клиента никогда не зависит от доступности нашего сервера.

## 1. Loader (инлайн-вставка)

- Клиент копирует `<script>…</script>` со страницы `/perf` в head сайта,
  **первым** скриптом. Никакого `<script src>` с нашего сервера: синхронная
  загрузка с внешнего хоста — ровно тот класс проблем, который мы ищем.
- Для обычного посетителя loader **не делает ничего**: проверяет `?arvexa`
  и куку и выходит. Никаких перехватов и наблюдателей — иначе мы сами
  нагружали бы всех посетителей (как amo-ym с его MutationObserver).
- Когда включён: ставит перехват вставки тегов (`Node.prototype.appendChild` / `insertBefore`,
  `Element.prototype.append/prepend/after/before/replaceWith`, сеттер `src`
  для `HTMLScriptElement`/`HTMLIFrameElement`/`HTMLImageElement`, `href` для
  `HTMLLinkElement`) и пишет в память кольцевой буфер: URL, тип тега, время
  вставки, стек вызовов (`new Error().stack`, обрезанный). Буфер ограничен
  (~300 записей), ничего не отправляется.
  и MutationObserver на документ (теги из исходного HTML и вставленные в
  обход перехвата), вешает на каждый тег `load`/`error`.
- Включение: `?arvexa=1` → ставит куку `arvexa_perf=1` (path=/, 7 дней) и
  асинхронно грузит `https://portal.arvexa.ru/perf/overlay.js`. `?arvexa=0`
  снимает куку. Без параметра и куки overlay не грузится.
- Вставка несёт версию (`ARVEXA Perf v1`). Overlay сравнивает с актуальной и
  при устаревании показывает «обновите код вставки».
- Логика в loader минимальна и стабильна — всё остальное в overlay, который
  обновляется сам.
- Перехват не должен ломать сайт: всё в try/catch, оригинальные методы
  вызываются всегда, возвращаемые значения не меняются.

## 2. Overlay (браузер)

Сборка = ядро `assets/arvexa-performance-overlay.js` + модуль «Сторонние
скрипты» + русский словарь + CSS.

### Изменения ядра (обратно совместимые, плагин на wp.org)

- `config.standalone`: без админ-бара, без серверных блоков (их и так нет
  без PHP-JSON), без отправки в историю; панель открывается через «пилюлю».
- `config.i18n`: объект `{__, sprintf}` вместо `wp.i18n`; ядро уже ведёт все
  строки через `__()` с английским текстом как ключом, standalone-сборка
  передаёт русский словарь. В WP — `wp.i18n`, как сейчас.
- В standalone ядро не запускает опрос серверного JSON, отправку истории и
  перехват fetch/XHR (он нужен только для WP AJAX), не пишет «No server
  data», а панель при первом включении открыта.
- Буфер loader'а (`window.__arvexaPerf`) модуль читает напрямую, ядру он не
  нужен.
- В WordPress всё выглядит и работает как раньше.

### Модуль «Сторонние скрипты» (`registerSection`)

- **Не отвечает**: URL вставлен (или найден в HTML), но через 5 с его нет в
  Resource Timing → красная строка «app.getreview.io не отвечает уже 34 с».
- **Кто подключил**: домен скрипта из стека в момент вставки — например
  «getreview ← stat1.clickfraud.ru». Для тегов из исходного HTML
  (находим перебором `<script src>`, `<iframe>`, `<link>` на странице)
  инициатор — «HTML страницы»; браузер не даёт перехватить их загрузку, и
  панель об этом честно пишет.
- **Блокирует отрисовку**: синхронные `<script src>` в head (без
  async/defer/module), `renderBlockingStatus` из Resource Timing, где есть.
- **Грузит процессор**: long tasks с привязкой к домену скрипта, где
  атрибуция доступна.
- **Что держит загрузку**: если `load` не наступил за 10 с — перечислить
  незавершённые запросы.
- **Справочник доменов**: человеческие имена и подсказки «что делать» для
  частых сервисов (Метрика, Mango, GetReview, intickets, clickfraud, Tilda
  CDN, VK, Mail.ru, Google Fonts…). Неизвестный домен показывается как есть.
- Кнопки: «Проверить с сервера» (→ probe), «Поделиться отчётом» (→ reports).

## 3. Сервер (portal.arvexa.ru, репозиторий arvexa-back)

Изолированный модуль по образцу `api/leads`: маршруты в `src/app/api/perf/`,
логика/схемы/CORS в `src/lib/perf/`. Не трогает сессии, Better Auth и данные
кабинета.

### Статика

- `public/perf/static/overlay.<hash>.js` / `.css` — `Cache-Control:
  immutable`, год (заголовки через `headers()` в next.config; nginx может
  отдавать эту папку напрямую — оптимизация, не требование).
- `public/perf/overlay.js` — крошечный указатель на актуальную хэш-версию,
  кэш 5 минут.

### `POST /api/perf/probe`

- Вход: `{ origin, hosts: string[] }`, не более 30 хостов.
- Для каждого параллельно (Node `dns`, `net`, `tls`): DNS → TCP:443 → TLS →
  первый байт ответа на `HEAD /`. Таймаут 8 с на хост. Сертификат:
  валиден / истекает < 14 дней / ошибка.
- Выход: фазы с таймингами и результат по каждому хосту.
- Защита от использования как сканера/SSRF:
  - только имена хостов (без IP-литералов, портов, путей; валидация zod);
  - порт всегда 443;
  - после DNS — отказ, если любой адрес приватный, loopback, link-local,
    CGNAT, multicast или адрес самого VPS; соединяться по проверенному IP
    (не резолвить повторно — защита от DNS rebinding);
  - кроме ClientHello и одного `HEAD /` ничего не отправляем;
  - лимиты: 10 запросов / 10 мин на IP, 30 / час на origin;
  - кэш результата по хосту 5 минут;
  - лимиты и кэш — в памяти процесса (один процесс Next на VPS), сброс при
    рестарте допустим.

### `POST /api/perf/reports` и `GET /perf/r/<id>`

- Снимок: URL страницы **без query и hash** (обрезается в браузере и
  повторно на сервере), метрики, домены, зависшие запросы, инициаторы,
  результаты probe, версия loader/overlay, user-agent. Никаких кук, данных
  форм, содержимого localStorage.
- `id` — 16 случайных символов (base62). Хранение 30 дней: просроченные
  удаляются при создании каждого нового отчёта, страница отдаёт 404 для
  просроченных (без cron).
- Prisma: модель `PerfReport { id, origin, json, ip, createdAt, expiresAt }`.
- Лимит: 5 отчётов / 10 мин на IP (подсчёт по БД, как в leads). Размер тела
  ≤ 200 КБ.
- Страница отчёта: read-only рендер той же панели на русском, `noindex`.

### CORS

Любой `Origin` (сайты клиентов заранее неизвестны), без credentials — куки
портала с чужих сайтов не уходят. Только `POST`/`OPTIONS` на `/api/perf/*`.

### Страница `/perf`

Код вставки с кнопкой «Скопировать», инструкции: Tilda (Настройки сайта →
Ещё → HTML-код для вставки внутрь head), обычный HTML-сайт, WordPress
(рекомендуем плагин). Как открыть панель (`?arvexa=1`), пример отчёта.

### Поведение при недоступности портала

Панель работает локально полностью; кнопки probe и «Поделиться» показывают
«сервер ARVEXA недоступен». Если не загрузился сам overlay — сайт работает
как обычно, панели просто нет.

## 4. Код и сборка

- Источник ядра и модуля — репозиторий плагина
  (`G:\работа\arvexa-performance-overlay`).
- Новые файлы в `standalone/src/`: `loader.js`, `third-party-core.js`
  (чистая логика, тесты на `node --test`), `third-party-section.js`,
  `i18n-ru.js`, `prelude.js`; сборка `tools/build-standalone.mjs`.
- `tools/build-standalone.mjs` склеивает и минифицирует ядро + модуль +
  словарь + CSS в `overlay.<hash>.js|css`, генерирует указатель
  `overlay.js`, минифицирует loader и кладёт всё в
  `G:\1212\arvexa-back\public\perf\` (+ текст вставки для страницы `/perf`).
- `docs/`, `tools/`, `standalone/` не должны попадать в пакет wp.org
  (`.distignore` + `export-ignore`).
- Модуль «Сторонние скрипты» в WordPress-версии пока выключен — включим
  отдельным релизом.

## 5. Проверка

1. Локальный стенд с зависшим доменом: мини-сервер принимает TCP и молчит,
   тестовая страница со скриптом-прокладкой вставляет к нему тег.
   Ожидаем: «не отвечает» через 5 с, инициатор — прокладка, `load`
   задержан, панель называет виновника.
2. Тесты probe: IP-литералы, порты, приватные адреса, домен с A-записью на
   127.0.0.1, rebinding, лимиты, кэш.
3. Реальные сайты до установки клиентом: minmagic.ru и wizardia.land с
   loader через DevTools Local Overrides — результат должен совпасть с
   ручной диагностикой (getreview, intickets синхронно в head, amo-ym
   MutationObserver в long tasks).
4. Регресс WP-плагина на стенде `C:\wp-local`: панель как прежде.
